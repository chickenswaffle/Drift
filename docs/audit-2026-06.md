# DRIFT security & architecture audit — June 2026

**Scope:** independent review of the DRIFT messenger codebase at `main` (post‑`v0.5.0`,
"Phase 6 Beacon" merged). Reviewed: `DESIGN.md`, `AGENTS.md`, `CHANGELOG.md`,
`drift/crypto/*`, `drift/transport/*`, `relay/*`, and `drift/storage.py`. No
`formal-models/` directory exists. The full test suite (325 tests) passes.

**Method:** read the design/claims first, then the implementation, then looked
specifically for (a) gaps between documented claims and code, (b) cross‑layer
composition bugs, (c) key‑management edge cases, (d) under‑stated "honest
limitations", and (e) untested adversarial paths. One finding (H1) was confirmed
with a throwaway proof‑of‑concept; no repository code was modified.

> **This is a review only.** Nothing below has been fixed. Suggested fixes are
> described, not implemented. Several findings interact — read H1, M1, and H3
> together, since they all stem from the same place: the layers authenticate
> *integrity* well but *peer identity* weakly, and the stealth/ratchet seam
> trusts material that any sender can forge.

---

## Summary

DRIFT's primitive‑level hygiene is good: it composes vetted libraries (PyNaCl /
`cryptography` / `argon2-cffi`), never rolls its own curve or AEAD math, lets
`InvalidTag` propagate, uses constant‑time compares where it matters, and
domain‑separates its HKDF `info` strings carefully. The panic vault's
two‑slot/constant‑work construction is genuinely well thought through. The
honesty culture in the docs is real and mostly accurate.

The problems are at the **seams**, which is exactly where a multi‑session,
layer‑by‑layer build is most likely to drift:

- **Two injectable denial‑of‑service holes.** A forged sealed message
  irrecoverably corrupts a victim's live ratchet (H1, PoC‑confirmed), and an
  *unauthenticated* relay burn wipes the shared firehose buffer for everyone
  (H2).
- **Two headline claims the code doesn't deliver.** Forward secrecy is broken
  for the opening burst of every conversation because the ratchet bootstrap is
  deterministic from long‑term keys (H3); and the duress/decoy deniability story
  is defeated because the real contact list is stored in plaintext on disk and
  never sealed (H4).
- **A documented key‑separation feature that does nothing** (the scan/spend
  split — M1) and **a privacy dial that does nothing** (FMD is unwired — M4).

None of these require breaking a primitive. They're composition and
documentation gaps. They are also fixable without a redesign.

Counts: **4 high, 5 medium, 4 low, 4 informational.**

## High

### H1 — A forged sealed message permanently corrupts the receiver's ratchet (injectable session DoS)

**Claim.** Sealed sender (`DESIGN.md` §5, `drift/crypto/sealed.py`) says the
recipient's one‑time address is bound as AEAD associated data so "the relay
cannot move a sealed blob onto a different address," and the ratchet
(`ratchet.py`) says "tampering with a header is rejected." The implication is
that a tampered message is cleanly rejected with no lasting effect.

**Location.** `drift/crypto/ratchet.py:213` (`ratchet_decrypt`) → `:276`
(`_dh_ratchet`); reached via `drift/transport/session.py:373‑378`
(`open_sender_header` → `ratchet_decrypt`); enabled by
`drift/crypto/stealth.py:150` (`derive_one_time_address`).

**Gap.** The sealed header is authenticated under
`seal_key = HKDF(stealth_key)`, where `stealth_key = ECDH(ephemeral_r,
scan_pub)`. That key is derivable by **any sender** from the victim's *public*
scan/spend keys — that is the whole point of a stealth address (anyone can mail
you). So the sealed‑header AEAD proves *integrity in transit*, **not** that the
header came from the real peer. Yet `ratchet_decrypt`, on seeing a header whose
`dh` differs from the current peer key, calls `_skip_message_keys` and
`_dh_ratchet` — which overwrite `root_key`, `their_ratchet_pub`, both chain
keys, and reset the counters — **before** the ratchet body is authenticated. If
the body then fails (it will, since the attacker doesn't know the root key), the
mutation has already happened and is not rolled back.

Result: any party who knows the victim's contact code (every contact, plus
anyone who resolves one of their beacons) can inject one well‑formed sealed blob
and **irreversibly desync the victim's live ratchet**. Confirmed with a PoC:
after the forged message is rejected with `InvalidTag`, the *next legitimate*
message also fails with `InvalidTag` — the conversation is bricked for the rest
of the session. (It self‑heals only because a new session re‑bootstraps
deterministically; see H3 for why that "heals" is itself a problem.)

This is the canonical Double‑Ratchet footgun the Signal spec warns about: state
transitions must be applied to a *trial copy* and committed only on a successful
decrypt. DRIFT mutates in place.

**Suggested fix.** Make `ratchet_decrypt` transactional: operate on a deep copy
of the relevant state (root key, chain keys, counters, `their_ratchet_pub`, and
the skipped‑key additions) and commit back to `state` only after `decrypt`
succeeds. Equivalently, derive the candidate message key without mutating, and
only perform the DH‑ratchet/skip side effects once the AEAD verifies. Add a
regression test that forges a header with a *new* `dh` and asserts the next
genuine message still decrypts (the existing `test_tampered_header_raises`
deliberately reuses the same `dh`, so it never exercises `_dh_ratchet`).

### H2 — Unauthenticated relay burn wipes the shared firehose for all users

**Claim.** `relay/server.py` `/burn` docstring and `CHANGELOG.md` 0.5.0 frame
burn as "best‑effort" and end‑to‑end verified: "The relay does NOT verify the
HMAC … Clients verify the token end‑to‑end before honouring the tombstone." The
framing implies the relay‑side action is benign.

**Location.** `relay/server.py:426‑468` (`burn_request`), specifically
`:463‑468` where the replay buffer is mutated before any token check is (or can
be) made.

**Gap.** The relay can't verify the token, but it still **acts on it**: for
`scope="conversation"` it executes `_recent[channel] = []`, and the channel is
the single shared firehose `drift-stealth-v1` (`session.py:78`). So *any*
anonymous party can `POST /burn` with `scope="conversation"`, `channel=
"drift-stealth-v1"`, and any 64‑hex string, and **erase the entire replay buffer
for every user on the relay**, repeatedly. The replay buffer is what closes the
subscribe‑race and late‑join delivery (`CHANGELOG.md` 0.4.4), so this is a
cheap, unauthenticated, global message‑delivery DoS. The token‑shape regex at
`:453` gates nothing security‑relevant — `"0"*64` passes.

A secondary issue lives in the same path: the broadcast tombstone echoes the
attacker's `token` to all subscribers (`:472‑476`). Clients correctly re‑verify
(`session.py:341`), so a bogus token can't force a client‑side delete — good —
but see M2 for why echoing *real* tokens is its own problem.

**Suggested fix.** The relay cannot authenticate a burn (no shared secret) and
the channel is shared, so a relay‑side buffer wipe is inherently
un‑authorizable in the current design — it should not be a relay action at all.
Options: (a) drop the relay‑side `_recent` mutation entirely and make burn
purely a client‑to‑client verified tombstone (the relay just forwards the
tombstone frame); (b) hold the buffer wipe until Phase 4's per‑recipient storage
exists, where a token can be scoped to one recipient's mailbox; (c) at minimum,
rate‑limit `/burn` and never let a conversation‑scope burn clear traffic that
isn't the requester's. Document that until then, `/burn` is an open DoS lever.

### H3 — Deterministic ratchet bootstrap breaks forward secrecy for every conversation's opening messages

**Claim.** `DESIGN.md` §4 / §10 headline: forward secrecy means "steal today's
keys and *past* messages remain unreadable." The ratchet docstring
(`ratchet.py:1‑29`) and `session.py:17‑45` describe the deterministic bootstrap
only as a *reliability* caveat ("if both peers send first … `InvalidTag`") and
say production would use X3DH (Phase 3).

**Location.** `drift/transport/session.py:180‑198` (`_bootstrap_ratchet`) and
`:200‑210` (`_promote_to_initiator`); `ratchet.py:151‑167` (`init_sender`).

**Gap.** The bootstrap is a pure function of long‑term keys:

```
root_secret      = HKDF(ECDH(my_spend, their_spend), "drift-ratchet-v1-root")
responder_keypair = HKDF(same ECDH, "drift-ratchet-v1-responder")   # deterministic
```

There is **no ephemeral secret that gets deleted** the way X3DH's one‑time
prekey is. An adversary who later compromises the long‑term spend key can
recompute `root_secret` *and* `responder_keypair`, and — using the initiator's
`dh` public key carried in the (now unsealed) header — reconstruct the first
sending chain and decrypt **every message sent before the first DH‑ratchet
turn**. In the common one‑directional open (Alice sends a burst before Bob
replies), that's the entire burst, for every session, retroactively, forever.
Because the responder keypair is identical across sessions, this is a standing
property, not a one‑off.

This directly contradicts the §10 forward‑secrecy claim *within the exact threat
model FS is supposed to cover* (later key theft). It is materially weaker than
X3DH and is not disclosed where FS is claimed — the docstrings frame
determinism as a "who speaks first" reliability quirk, not an FS hole.

**Suggested fix.** Short term, document it honestly next to the FS claim:
"forward secrecy applies from the first DH‑ratchet turn onward; messages sent
before the peer's first reply are recoverable if the long‑term spend key is later
compromised." Medium term, implement the planned X3DH with published, rotated,
deleted one‑time prekeys so the opening messages get a deleted ephemeral
contribution. At minimum, mix a *fresh, deleted‑after‑use* ephemeral from the
initiator into `root_secret` (sent in the first header) so the static ECDH alone
no longer reconstructs the opening chain.

### H4 — Duress/decoy deniability is defeated: the real contact list is plaintext on disk and never sealed

**Claim.** `DESIGN.md` §8: "Decoy contacts and hidden volumes — a real set of
chats behind your true passphrase, an innocuous set behind the duress one. A
forced device unlock reveals nothing real." `panic.py` and `storage.py` describe
a vault whose mere presence reveals nothing and a decoy that "looks lived‑in."

**Location.** `drift/storage.py:101‑106` (`save_contacts` — plaintext),
`:181‑190` (`_materialize` — decoy/real both write/leave plaintext contacts),
`:265‑281` (`lock` — explicitly leaves contacts on disk), `:324‑325` (decoy
unlock materializes decoy contacts but does not remove the real ones).

**Gap.** Only the **identity** is sealed in the vault. **Contacts are never
sealed** — `save_contacts` writes `contacts/<scan_pub>.json` in cleartext
(chmod 600) every time the user runs `drift add`, and `lock()` deliberately does
not shred them. So:

- After any normal use, the user's entire real contact graph (names → contact
  codes) sits in plaintext on disk regardless of the vault.
- In **decoy** mode, `unlock` swaps `identity.json` to the decoy but leaves the
  real `contacts/<real_scan_pub>.json` file in place. A coercer who is handed
  the duress passphrase, then lists `~/.config/drift/contacts/`, sees **two**
  contact files — the decoy's and a second one that doesn't match the
  "current" identity. That both leaks the real contact graph *and* is a tell
  that a hidden identity exists, which is precisely what the decoy is meant to
  prevent.

The metadata DRIFT works hardest to protect on the wire (who talks to whom) is
left unprotected at rest, under a feature that explicitly promises a forced
unlock "reveals nothing real."

**Suggested fix.** Seal contacts inside the vault payload alongside the identity
(the payload already round‑trips JSON and is padded to 4 KiB — `PAYLOAD_SIZE`
may need raising or a separate sealed contacts blob). On `lock`/duress, shred
*all* `contacts/*.json`, not just `identity.json`. In decoy mode, ensure the
real contacts file is removed/sealed so only the decoy's exists. Until then,
document plainly that the contact list is not protected at rest and the decoy
does not hide it.

## Medium

### M1 — The scan/spend key split provides no privilege separation; the scan key alone decrypts everything

**Claim.** `DESIGN.md` §2: scan key "lets others derive one‑time addresses *to*
you; lets you **detect** your mail"; spend key is "the secret that actually
**unlocks** a detected message," and "you could one day hand a *scan‑only* key
to a low‑power device to filter your mail without ever giving it the power to
read." `AGENTS.md` repeats this. `stealth.py`'s header math
(`A_once = spend_pub + Hash(s)·G`) suggests the spend secret is algebraically
required to recover a message.

**Location.** `drift/crypto/stealth.py:175‑199` (`scan_for_message`) and
`:117‑143` (`_spend_point` / `_address_from_secret`).

**Gap.** In the implementation the message key is
`derive_message_key(ECDH(scan_priv, R))` — it depends only on the **scan**
secret. `scan_for_message` takes `my_scan_priv` and `my_spend_pub` (the *public*
spend key); the spend **private** key is never used to detect *or* decrypt
anything. And the address point isn't really `spend_pub` as a curve point — it's
`B = Elligator(SHA256(tag ‖ spend_pub))`, a deterministic tag with no algebraic
link to the spend *private* key. So:

- Possession of `scan_priv` alone is sufficient to read all messages.
- The spend private key contributes **zero** confidentiality.
- The advertised "scan‑only delegation to a low‑power device" would, if built as
  designed, hand that device the ability to **read everything**, not just
  filter.

This isn't remotely exploitable today (you still need the scan key, which is
secret), but it nullifies a documented defense‑in‑depth property and is a loaded
footgun for anyone who implements the delegation feature trusting the docs.

**Suggested fix.** Either (a) make the docs match the code — state that
confidentiality rests on the scan key alone and that "scan‑only" delegation is
*not* safe — or (b) make the code match the docs by binding the message key to
the spend secret too (e.g. a second ECDH against the spend key, or a Monero‑style
construction where recovering the one‑time *private* key requires the spend
scalar). Option (b) is the larger change but is the only one that delivers the
claimed separation.

### M2 — Conversation burn token is a stable, eternal, cleartext conversation fingerprint (and replayable forever)

**Claim.** `burn.py` and `CHANGELOG.md` 0.5.0 present burn tokens as
domain‑separated MACs that clients verify; nothing flags them as long‑lived
identifiers.

**Location.** `drift/crypto/burn.py:39‑58` (`generate_burn_token`),
`drift/transport/session.py:320‑324` (`burn_conversation`),
`relay/server.py:472‑491` (tombstone broadcast including `token`).

**Gap.** A conversation‑scope token is `HMAC(HKDF(static_ECDH), "conversation:")`
— a **fixed value for the life of the conversation** (static keys → static
token), with no nonce, timestamp, or counter. The relay then **broadcasts it in
cleartext** to every subscriber on the shared firehose. Consequences:

- **Linkability:** the same token appears every time either party burns the
  conversation, so any firehose observer can cluster a pair's burn events over
  time — a stable per‑conversation tag, which is exactly the kind of correlation
  the rest of the design works to eliminate.
- **Replay:** because the token never changes and clients accept any
  cryptographically valid token (`session.py:341`), anyone who captured one real
  conversation tombstone can replay it indefinitely to force both clients to
  re‑burn that conversation.

**Suggested fix.** Bind the token to a freshness value the verifier also checks:
include a timestamp/epoch and a random nonce in the MAC input and in the
tombstone, reject stale/replayed nonces client‑side, and do not derive burn
authority from a value that is then published in the clear. Long term, scope
burns per‑message (those tokens are already address‑bound and unique) and avoid a
single static conversation token altogether.

### M3 — Beacon confidentiality is offline‑grindable indefinitely, not just "while lit"

**Claim.** `DESIGN.md` §5 (Beacon) and `beacon.py` say a guessable handle is
"dictionary‑grindable for as long as the beacon is lit (up to 10 minutes), at
which point it links to your contact code," and that after TTL the entry is
deleted "no retroactive way to discover who was behind it."

**Location.** `drift/crypto/beacon.py:103‑104` (`_encryption_key` =
`HKDF(handle)` — no salt), `:139` (encrypt under handle‑only key).

**Gap.** The payload key derives **solely from the handle**, with no salt and no
binding to time. Decryption is entirely offline. A logging or malicious relay
(or any peer that received the gossiped beacon) can **retain the ciphertext past
expiry and grind it forever**: for any guessable handle it recovers the contact
code at leisure, with no 10‑minute bound. The "deleted after TTL → no retroactive
lookup" property holds only for an *honest* relay that actually deletes; the
crypto provides no such guarantee. The real limitation is therefore stronger than
documented: a weak handle is permanently grindable by anyone who kept the blob,
not just during the lit window.

**Suggested fix.** State the real bound: a captured beacon blob is offline‑
grindable indefinitely; the time‑box is a policy of honest relays, not a
cryptographic property. To raise the cost, run the handle through a memory‑hard
KDF (Argon2id, as the panic module already does) instead of HKDF so each
dictionary guess is expensive, and/or require a high‑entropy handle for the
feature at all. None of these fully fix a low‑entropy handle — say so.

### M4 — The FMD privacy dial is unwired: `drift privacy --fmd-rate` changes nothing on the wire

**Claim.** `DESIGN.md` §8 and `storage.py`/`cli.py` present FMD as "a literal
privacy/efficiency dial the user can turn"; `cli.py privacy` stores `fmd_rate`
and prints reassuring status.

**Location.** `drift/crypto/fmd.py` (complete library), `drift/storage.py:348‑369`
(`get/set_fmd_rate`), `drift/cli.py` `privacy`. **No caller** — `fmd_flag`,
`fmd_test`, `generate_fmd_key` are referenced nowhere in `drift/transport/*` or
`relay/*` (verified by grep). The relay `/send` path has no flag field and no
pre‑filter.

**Gap.** Setting an FMD rate has **no effect on any message or any relay
behavior**. A user who turns the dial up may believe they've changed their
anonymity/efficiency tradeoff when nothing has changed. For a privacy tool, a
security control that silently does nothing is worse than an absent one. (The
FMD2 implementation itself looks faithful to the cited paper and is well tested
in isolation — the problem is purely that it isn't connected.)

**Suggested fix.** Either wire it (sender attaches `fmd_flag(message_or_addr,
detection_pub)` to the envelope; recipient hands the relay a `downgrade`d
detection key; relay pre‑filters before fan‑out) or, until then, mark the dial
clearly as experimental/no‑op in the CLI and docs so it doesn't convey false
assurance.

### M5 — Safety number commits only to scan keys, not spend or identity keys

**Claim.** `storage.py:138‑150` `safety_number` is "the short out‑of‑band
verification phrase," the value `drift verify` compares to detect a
man‑in‑the‑middle; `DESIGN.md` §7 shows it as the trust anchor.

**Location.** `drift/storage.py:146‑150`.

**Gap.** The digest covers only the two **scan** public keys
(`sorted([my_scan, their_scan])`); it omits the spend public key and the Ed25519
identity/verify key. So out‑of‑band verification does **not** fully bind the
contact code: a contact code carrying the real scan key but a substituted spend
key produces the *same* safety number and passes verification. (A spend swap
breaks message *delivery* rather than enabling interception, so the practical
risk is limited — but the verification step is exactly where the user is told
"these keys are really theirs," and it isn't checking all of them.) It also means
the Phase‑6 beacon signing key, derived from the spend key, is never anchored by
verification.

**Suggested fix.** Hash all public key material into the safety number — both
scan and spend public keys (and, once it's a first‑class field, the identity
verify key) — keeping the sorted/symmetric construction.

## Low

### L1 — `Session._seen_addrs` grows without bound
`drift/transport/session.py:164` accumulates every accepted one‑time address for
the life of a session with no eviction. A long‑lived chat slowly leaks memory.
Bound it (e.g. an LRU/`deque` of recent addresses) — the dedup only needs to
cover the replay window, which is ≤ 30 s on the full relay.

### L2 — Duress *wipe* is distinguishable across repeated unlocks
`drift/storage.py:284‑331`: wipe mode shreds the vault and materializes a fresh
random identity. If a coercer forces a second unlock, there is now *no vault* and
a *different* identity than the first prompt — observable differences the
"indistinguishable" framing doesn't cover. Document the single‑shot nature of
wipe, or have wipe leave a plausible decoy vault in place.

### L3 — Relay `/send` accepts unbounded `ct`/`addr`
`relay/server.py:265‑316` performs no size or shape validation on `ct`/`addr`
before buffering up to `RECENT_MAX` (500) envelopes per channel. A client can
park 500 large blobs in memory per channel. Cap envelope size and validate that
`addr` decodes to 32 bytes.

### L4 — Spend private key is reused as both an X25519 DH key and an Ed25519 seed source
`crypto/__init__.py:210‑221`: the Ed25519 signing seed is `HKDF(spend_priv)`,
while `spend_priv` is also used directly as an X25519 DH key in the ratchet
bootstrap. Using one secret in two algebraic settings is generally tolerated when
one path is hashed (this is), but it couples the signing identity's compromise to
the spend key and vice versa. Consider an independent stored Ed25519 key, or at
least note the coupling.

## Informational

- **`stealth.py` module docstring is stale** (`:1‑61` still says "documented
  placeholder," describes Ristretto/`pure25519` options not used, and an outdated
  payload format). `AGENTS.md` already flags this; worth fixing so the file
  doesn't mislead a contributor about which scheme is live.
- **`BeaconPayload.lookup_hash` docstring says "hex SHA256(handle)"**
  (`beacon.py:79`) but the value is `SHA256(prefix ‖ handle)`. Cosmetic, but in a
  module whose security argument *is* the domain‑separation prefix, the comment
  should be exact.
- **Test coverage gaps on adversarial paths.** The suite is strong on happy‑path
  and integrity (`InvalidTag` on tampered ct/header, forward‑secrecy, skipped‑key
  bounds), but has **no test** for: (a) the H1 state‑corruption path — a forged
  header with a *new* `dh` followed by a genuine message (`test_tampered_header_
  raises` reuses the same `dh` and so misses it); (b) the H2 unauthenticated relay
  burn wiping the shared buffer; (c) FMD having no on‑wire effect (M4); (d) a
  decoy unlock leaving the real contacts file on disk (H4). Adding these would
  have caught four of the findings here.
- **What's solid, stated explicitly so the report isn't all red:**
  - Primitive discipline holds throughout — no hand‑rolled curve/AEAD/HMAC; the
    iron rules are respected.
  - AEAD associated‑data binding is used correctly (ratchet header bound to the
    body; one‑time address bound to the sealed header).
  - Constant‑time compares are used where they matter (`stealth.scan_for_message`,
    `burn.verify_burn_token`, the panic vault's both‑slots‑always path).
  - The panic vault's indistinguishability design (two slots always, random
    second slot when no duress, randomized order, fixed‑size padding, identical
    KDF work, no early return in `try_unlock`) is careful and correct *for the
    at‑rest identity* — its weakness is scope (contacts, H4), not construction.
  - `resolve_beacon` defends against a relay serving a mismatched payload
    (signature + `handle` equality + expiry + contact‑code parse checks), and the
    relay's beacon TTL cap is enforced server‑side regardless of the request.
  - Federation dedup is content‑addressed over client fields only, so it neither
    loops nor leaks anything the relay didn't already forward.
  - The `R`‑is‑public sealed‑sender limitation is disclosed accurately and is the
    correct, unavoidable shape for an ECDH stealth scheme.

---

## Recommended order of work

1. **H1** (transactional `ratchet_decrypt`) — small, self‑contained, kills an
   injectable session DoS and is pure correctness.
2. **H2** (remove/scope the relay‑side burn buffer wipe) — small, kills a global
   unauthenticated DoS.
3. **H4** (seal contacts; shred them on lock/duress) — medium, restores a
   marketed safety property people may rely on under coercion.
4. **H3 / M1 / M2 / M3 / M5** — correctness *and* honesty: where the fix is
   large (X3DH, spend‑key binding), update the claims now and schedule the code.
5. **M4** — wire FMD or label it non‑functional.
6. Low / informational as cleanup.

## Resolution update — 2026-06-12 (v0.10.0)

The four **high‑severity** findings were fixed, each as its own commit with the
full test suite (now **336 passing**), `ruff`, and `mypy` green between them. This
section is appended, not a rewrite — the analysis above stands as written at
audit time. H1 was re‑confirmed with a PoC before the fix and the PoC no longer
reproduces after it.

### Resolved

- **H1 — ratchet state corruption — RESOLVED.** `ratchet_decrypt` now runs on a
  snapshot and commits the advanced root/chain keys and DH‑ratchet step back to
  the live state only on a successful authenticated decrypt. A forged/tampered
  message (including one naming a fresh DH key) leaves the ratchet byte‑for‑byte
  unchanged. Regression tests: forged‑new‑DH rejected then next genuine message
  still decrypts; full state identical after a rejected forgery.
  (`drift/crypto/ratchet.py`, commit `fix: H1 …`.)

- **H2 — unauthenticated `/burn` DoS — RESOLVED (with a documented, bounded
  residual).** The relay no longer wipes the shared firehose buffer on a
  conversation‑scope burn; it deletes only the single blob whose one‑time
  address is explicitly named (message scope). Conversation erasure is now purely
  the end‑to‑end‑verified tombstone plus the buffer's own TTL. Regression test:
  an anonymous burn can't drop another user's queued message.
  *Residual (unchanged, now documented in DESIGN.md "Burn requests"):* because a
  one‑time address is public on the firehose, a connected subscriber can still
  evict an individual blob it *observed* from the ≤30 s replay buffer — bounded,
  self‑healing, never affects an already‑delivered message, and only fully closed
  by Phase 4 authenticated per‑recipient storage.

- **H3 — bootstrap forward‑secrecy gap — FULLY CLOSED (v0.14.0).** Both the
  sender‑side gap and the recipient‑side residual are now eliminated by the X3DH
  handshake (see the v0.14.0 update below). The original sender‑side fix is kept
  here for the record. The initiator folds a fresh,
  single‑use ephemeral (private half discarded immediately, never stored or
  derived from the long‑term key) into the bootstrap root, carried to the peer in
  the sealed envelope of every bootstrap‑chain message. The opening burst is now
  forward‑secret against compromise of the **sender's** long‑term spend key.
  *Residual (fundamental, documented in DESIGN.md §4):* compromise of the
  **recipient's** long‑term spend key still opens the opening burst — unavoidable
  when messaging someone from their long‑term key alone with no prior round trip.
  **Full closure requires interactive prekeys (X3DH) — see follow‑up below.**

  **Update — 2026‑06‑17 (v0.14.0): recipient‑side residual CLOSED via X3DH.** The
  deterministic bootstrap is gone as the default. DRIFT now implements the Signal
  **X3DH** handshake (`drift/crypto/x3dh.py`, `drift/transport/session.py`): every
  user publishes a signed prekey + a batch of one‑time prekeys to the relay
  (`/prekeys/*`), sealed at rest in the vault (the H4 pattern) and shredded on
  lock/decoy/wipe. The initiator fetches the bundle, verifies the Ed25519
  signature, runs `DH1..DH4 → HKDF`, and the recipient's signed prekey becomes the
  initial ratchet key. The relay hands out each **one‑time prekey exactly once and
  deletes it**, and the recipient consumes it on receipt — so the opening‑burst
  master secret depends on an ephemeral private (the OTPK) that no longer exists
  anywhere. A later compromise of **either** party's long‑term keys therefore can
  no longer reconstruct it. The X3DH‑receive path is transactional (an OTPK is
  burned and the ratchet swapped only after the bootstrap message authenticates),
  preserving the H1 anti‑corruption guarantee. The earlier deterministic bootstrap
  survives **only** as a visibly‑warned fallback for peers who have published no
  bundle (old client / expired). Regression test
  (`tests/unit/test_x3dh.py::TestForwardSecrecyClosesH3`): after establishment and
  OTPK deletion, the opening master secret is unrecoverable from everything the
  recipient still holds.

  The one remaining operational gap — a long‑online recipient whose published
  one‑time prekeys are drained by many senders, after which the relay would serve
  weaker OTPK‑less bundles — is also closed: the session **auto‑replenishes the
  relay‑side pool mid‑session** (in the background, after each consumed OTPK and
  once at startup) whenever it dips below the low watermark, so the strong X3DH
  path never silently degrades (`tests/integration/test_e2e.py::test_otpk_pool_auto_replenishes_mid_session`).
  With this, **H3 is fully closed — sender side, recipient‑side residual, and the
  prekey‑exhaustion edge.**

- **H4 — duress/decoy contact leak — RESOLVED.** Contacts are sealed in the vault
  alongside the identity. `lock(passphrase)` re‑seals the opened slot (preserving
  the untouched duress slot) and shreds the plaintext identity *and* every
  contacts file; `unlock` restores sealed contacts and a decoy unlock shreds any
  prior identity's contacts first. Regression test mirrors the wipe‑irrecoverability
  pattern: after a decoy unlock the real contact code appears nowhere on disk.
  *Residuals (documented in DESIGN.md §8 and the panic module):* plaintext while
  unlocked (inherent — `lock`/close restores at‑rest protection), `secure_overwrite`
  best‑effort on exotic storage, and a multi‑image longitudinal diff that is
  outside the single‑image threat model.

### Still open — require the medium/low follow‑ups

The high‑severity fixes did **not** touch these, and two of them now interact
with the new code:

- **M1 (scan/spend no privilege separation)** — open. The spend key is the
  beacon‑signing seed (and, before X3DH, also bore the opening‑burst residual —
  now closed), so it matters more than before — yet confidentiality still rests on
  the scan key alone. Worth resolving the docs‑vs‑code gap.
- **M2 (conversation burn token is a stable, replayable fingerprint)** — partially
  reduced, not closed. H2 removed the relay‑side blast radius, but the token is
  still broadcast in the tombstone and is still a static per‑conversation value a
  captured copy can replay to force client‑side re‑burn (and cluster a pair's
  burns over time). Needs a freshness/nonce binding.
- **M3 (beacon offline‑grindable indefinitely)** — open.
- **M4 (FMD dial is unwired)** — open.
- **M5 (safety number commits only to scan keys)** — open, and now more pointed:
  the beacon signing key rests on the spend key, yet out‑of‑band verification still
  doesn't bind it. Hash scan **and** spend (and the identity verify key) into the
  safety number.
- **L1–L4** — open (unbounded `_seen_addrs`, wipe single‑shot tell, unbounded
  `/send` blob size, spend‑key reuse coupling).

### Recommended next step

~~**X3DH with published, rotated, one‑time prekeys** is the single highest‑value
follow‑up~~ — **done in v0.14.0** (see the H3 update above): X3DH closes the
recipient‑side residual (true forward secrecy from the very first message) and
demotes the deterministic bootstrap to a visibly‑warned legacy fallback. The
remaining open items are the medium/low follow‑ups (M1–M3, M5, L1–L4).

## Resolution update — 2026-06-18 (v0.14.1)

The remaining **medium** findings (M1, M2, M3, M5) and the two straightforward
**low** findings (L1, L3) are fixed, each in severity order with the full suite
(now **513 passing**), `ruff`, and `mypy` green between them. No new primitives
were introduced (project iron rule) — every fix composes the existing
libsodium/`cryptography` HKDF, HMAC, X25519, and Ed25519 building blocks. The two
remaining lows (L2, L4) require architectural changes and are documented as
deferred. M4 was already wired (see DESIGN.md §8 / the M4 entry above).

### Resolved

- **M1 — scan/spend privilege separation — RESOLVED.** The stealth message key is
  now `HKDF(ECDH(scan, R) ‖ ECDH(spend, R))` instead of `HKDF(ECDH(scan, R))`.
  The one‑time *address* is still derived from the scan DH alone, so detection is
  unchanged — but decryption now requires the private *spend* key. `scan_for_message`
  returns a `ScanResult` (confirmed ownership + the intermediate scan secret); a
  second step, `derive_message_key_with_spend`, folds in `ECDH(spend, R)` to produce
  the key. A device holding only the scan key can confirm a message is addressed to
  it but cannot read it — the documented "scan‑only delegation" is now real. Breaking
  on the wire (the derived key changes), so peers must both run ≥ `v0.14.1`.
  (`drift/crypto/stealth.py`, `drift/transport/session.py`; new tests in
  `tests/unit/test_stealth.py::TestScanSpendPrivilegeSeparation`; DESIGN.md §2/§3.)

- **M2 — burn token replay/linkability — RESOLVED.** Burn tokens are single‑use:
  `generate_burn_token(..., nonce=None)` now mints a fresh `os.urandom(16)` nonce and
  a timestamp, both bound into the HMAC and carried in the wire token
  (`nonce.timestamp.mac`). The relay tracks seen nonces in a bounded LRU (the
  federation dedup pattern) and rejects replays, and rejects tokens whose timestamp is
  outside a 300 s window; the client re‑verifies the MAC and the freshness window. A
  captured token is therefore either stale or already‑burned, and the conversation
  token is no longer a stable per‑conversation fingerprint. (`drift/crypto/burn.py`,
  `relay/server.py`; tests in `test_burn.py`, `test_relay_burn.py`.)

- **M3 — beacon lookup hash relay‑specific — RESOLVED.** The index hash is now
  `SHA256("drift-beacon-lookup-v1" ‖ relay_pubkey ‖ handle)`, where `relay_pubkey` is
  the relay's long‑term Ed25519 key fetched from the new `GET /beacon/pubkey` (an alias
  of `/witness/pubkey`). A rainbow/dictionary table built against one relay is useless
  against another, so grinding which handles exist now costs one table *per relay*. The
  honest residual — a captured encrypted payload is still offline‑grindable indefinitely
  because the payload key is `HKDF(handle)` — is documented, not silently implied.
  (`drift/crypto/beacon.py`, `relay/server.py`, `drift/cli.py`, `drift/ui/app.py`;
  tests in `test_beacon.py`, `test_relay_beacon.py`.)

- **M5 — safety number scope — RESOLVED.** `safety_number` now digests
  `SHA256("drift-safety-v1" ‖ sorted([my_scan‖my_spend, their_scan‖their_spend]))` —
  both scan and spend public keys, keeping the sorted/symmetric construction. A contact
  code that kept the real scan key but swapped the spend key (the X3DH identity key and
  beacon signing seed) used to produce an identical number and pass `drift verify`; it
  no longer does. **Migration:** every pre‑`v0.14.1` safety number is invalidated —
  contacts must re‑verify out of band. The `drift verify` CLI and the UI verify modal
  surface this note. (`drift/storage.py`, `drift/cli.py`, `drift/ui/app.py`; tests in
  `test_storage.py`; DESIGN.md §2/§7.)

- **L1 — unbounded `_seen_addrs` — RESOLVED.** The per‑session one‑time‑address dedup
  set is now a bounded `_BoundedAddrSet` (OrderedDict‑backed, cap 4096, oldest‑evicted).
  The dedup only needs to span the relay's ≤30 s replay window, so a long‑lived chat no
  longer leaks memory. (`drift/transport/session.py`; tests in `test_transport.py`.)

- **L3 — unbounded `/send` blob — RESOLVED.** `/send` now rejects a `ct` larger than
  `MAX_CT_B64_LEN` (64 KiB base64) with `413`, and rejects an `addr` that doesn't decode
  to exactly 32 bytes with `400`. The relay still never reads the blob — it only bounds
  size and validates the routing‑tag shape. (`relay/server.py`; tests in
  `test_relay_federation.py`.)

### Deferred (documented, not fixed — would require architectural change)

- **L2 — wipe distinguishable across repeated unlocks.** The duress *wipe* is
  single‑shot: a second forced unlock reveals no vault and a different identity than the
  first. The indistinguishability guarantee covers one forced unlock. Making wipe leave a
  convincing decoy vault behind touches the live constant‑work two‑slot panic vault and
  risks weakening it, so it is deferred; the limitation (and the recommendation to use the
  *decoy* variant where a second unlock is plausible) is now documented in DESIGN.md §8.

- **L4 — spend key reused as X25519 DH + Ed25519 seed.** The signing key is `HKDF(spend_priv)`
  while `spend_priv` is also a raw X25519 DH key. The hashed signing path makes this
  tolerable, but it couples the two compromises. An independent stored Ed25519 key would
  decouple them but changes the on‑disk identity format and needs a migration, so it is
  deferred; the coupling is now stated explicitly in DESIGN.md §2.
